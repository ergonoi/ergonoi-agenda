# Decision log

What was decided while building οὐθείς Agenda, why, and which alternatives were rejected. The specifications (`architecture.md`, `ui.md`) describe the current state; this file keeps the reasons, so that the history can be followed without the conversations in which it was worked out. Newest topics are not necessarily last; entries are grouped by subject. Commit hashes refer to this repository.

## 1. Working rules for this repository

These apply to everyone who changes the repository, including AI assistants.

- **Ask before changing.** A change is described in two or three sentences, with what depends on it, and made only after approval. Larger interface changes are shown as a mockup first.
- **English in code and project files** (names, comments, messages, documentation). Content in other languages appears only as user content.
- **No personal data in the repository.** No real names, facets, topics, addresses or journals of a person, so that the project can be used by anyone. Personal material belongs in `human/` (git-ignored; the name follows outheis-beta and is deliberately not a hidden dot directory). Where `human/` provides nothing, generic defaults apply.
- **Naming.** The service and the application are called *Agenda*, displayed as *οὐθείς Agenda*. The earlier name *Notes* (repository `outheis-notes`) is not used anywhere any more.
- **Fonts are self-hosted or embedded.** No Google Fonts, not even by link.
- **No grey fills**, with one exception chosen deliberately: the side areas on wide screens (`#F8F7F7`). Dialogs use a white veil, not a grey backdrop.
- **Repositories of outheis** (`outheis-beta`, `outheis-docs`) are only read for reference, never changed from here.

## 2. Architecture

### 2.1 The service holds no key (commits a119d32, 2a5f5f2)

An early pilot let the server hold the key, read the journal and merge it. It was rejected: a server that can read is a server that must be trusted, and it limits who can be offered the service. Decision: the service is a pure relay. It stores encrypted lines per account, never reads, merges or compacts. Clients encrypt (AES-GCM per line, padded to 256 bytes so that lengths reveal little), merge, and compact by replacing the file with `If-Match`. Client-side encryption was also chosen for architectural freedom: any client that has the phrase can work with the file, with or without the service.

### 2.2 Account phrase instead of user names (architecture 8.2)

Considered: a user UUID (as in Signal), or a hash of a password. Chosen: eight English BIP39 words generated by the first client. They can be written down and typed on another device; a QR code is not required, because many devices that use the agenda have no camera. From the phrase the client derives the encryption key and an access token; the account name on the service is `hex(SHA-256(token))`. Consequences:

- The *account ID* can be given to the operator to find a file; it grants no access (the token cannot be computed from its hash).
- Knowing the ID, a script gets nothing; with the stored file but without the phrase, guessing 88 bits through PBKDF2 is impractical.
- Losing the phrase loses the journal. Nobody can restore it.
- A codeword for operator lookups was considered and dropped; the account ID serves that purpose.

### 2.3 Abuse limits fixed in the binary (architecture 8.4)

An open relay that stores opaque data invites misuse (dead drops, illegal content). Limits: 5 MB per account, fixed in the binary (raising it means recompiling; never above 10 MB); lines of a fixed format and at most 4096 bytes; rate limits per account and per IP; at most 10 new accounts per IP and day; accounts deleted after five years without access.

### 2.4 Local use without the service (architecture 8.7)

Required: a client must be able to open the encrypted file directly, without a service, e.g. when the file is handed to someone who uses it only locally, or when the service is gone. The web client therefore has *Open local journal*, *Export journal file* (encrypted, optionally plain text) and an *Account ID from a phrase* function. Phones need not support local files.

### 2.5 Compaction only by clients (architecture 6.4, 8.5)

The service cannot compact because it cannot read. A client compacts and overwrites the file with `If-Match`; a concurrent change makes the write fail (412) and the client retries later.

### 2.6 Deployment (deploy/DEPLOY.md)

A Hetzner x86_64 host with nginx and certbot in front; the service listens on a non-standard local port (`127.0.0.1:41380`, not 8080) as system user `agenda`, data in `/var/lib/agenda/accounts`. The guide is written so that the setup can be reproduced exactly elsewhere. The web client is embedded in the binary; deploying means replacing one file.

## 3. Journal and grammar

### 3.1 No header, no front matter (architecture 3.4)

The journal is lines only. A header for settings or vocabulary was rejected: it breaks the line model and merging. Clients derive facets and topics from the lines themselves.

### 3.2 Keeping tag values: Tag definitions (`#type-meta`; dated 3000-12-31 before 0.5.0)

Problem: a value that no open entry uses disappears once closed entries are compacted, so rarely used facets and topics would be lost. Considered: a header (rejected, 3.1). Chosen: entries `Tag definition: <description> … #type-meta`. They live in the journal like any entry, are merged and encrypted, never appear in a view (views end three months ahead), and can be edited by hand. The date is fixed to 31 December 3000 rather than "100 years ahead" so that it never moves. The same pattern is used for `Journal name:` and `Learned Rule:`. These entries need no facet.

### 3.3 Horizon and groups (ui.md 5.4)

Views cover at most three months. Groups: Today (with overdue) 5, Tomorrow 5, Next 7 days 10, Later (to day 30) 10, each expandable; items with a clock time are exempt from the caps; recurring items appear at their next occurrence; each item appears once. A missing rank counts as medium. Real weighting of relevance across several professions and family life is left to a language model following rules in `human/` (architecture, open issue 7), because fixed heuristics are not sufficient.

### 3.4 Defaults for new accounts (ui.md 4.11c)

A new account gets its journal name (asked for at creation), Tag definitions for the facets `private` and `work` and the topics `sports`, `official`, `travel`, and four example entries. Earlier defaults (`work`, `family`, `self`) were replaced by these.

## 4. Interface

### 4.1 Layout

- **No kanban or column boards** ("Trello"): rejected from experience. Groups stay one below the other, like notes on paper. No manual ordering either (it would need predecessor/successor tags).
- **Wide screens:** one row per item — a date/time column (190 px), the text, all tags — with dates shown in every group, at most 1200 px wide, side areas `#F8F7F7`. Vertical lines at the column edges were rejected.
- **A navigation bar** with setup and settings as in-page views was rejected as confusing; dialogs remain.
  *Superseded for the settings (16 November 2026):* the header has since become a row of view tabs and icons (the filter is a view), and the settings dialog had grown into a mix of unrelated functions. Settings are now a view with sections (Journals, Account, Import and export, Work locally, Log); its sub-dialogs stay dialogs, and the setup at first start stays a dialog, as there is no list to return to yet.

### 4.2 Colours and type

- Header in Pearl Aqua `#97EAD2`: the most readable of the options shown (Wisteria, Amber, Scarlet; Scarlet reads as alarm).
- Buttons: primary Dark Amethyst, secondary Wisteria `#C490D1` (white buttons on white were hard to see), ghost, danger with a Scarlet outline.
- Buttons that choose a tag are not filled (white, silver border, facet colour stripe); filled violet there was disliked. *+ New facet* and *Add* may be violet: they are actions.
- Facet stripe on items 6 px (3 px was too thin). Rows without a facet (group headings, *more*, *Show fewer*) carry a 6 px stripe in Mist `#E8E6E6`, so that the coloured stripes do not end abruptly against white; Fog `#F4F3F3` was tried first and was too faint to see.
- Fonts follow outheis.com: IBM Plex Sans for text, Inter for the name and headings (it carries the Greek of οὐθείς), IBM Plex Mono for monospace. All embedded or self-hosted from `clients/web/fonts`.
- Icon: an "A" in Inter 600, Dark Amethyst, centred, on a background one third Pearl Aqua (top) and two thirds Wisteria.

### 4.3 Entering values

- **Prefixed fields.** Every field for a new value shows the fixed prefix in light grey (`#facet-`, `#topic-`, `#date-`, `#time-`, `#recurring-`), so that the complete stored tag is visible while only the value is typed. Without it, users produce malformed tags.
- **Every allowed form can be entered**: date as text plus a calendar button; time as point, span or duration; all recurrence patterns; a second date (*end date*) for multi-day spans.
- **The new-value field comes first** in the menu, because below a long list of values it was unreachable on a phone.
- **A value created in such a field gets a Tag definition at once**: what someone deliberately creates should not vanish after the retention period. Values that arrive in typed text or by import do not.
- **A `?` next to these fields** explains what happens to a new value and how to remove it, because the conventions cannot be guessed.
- **Dictation** starts a new session per tap and keeps interim results; placeholder "New item — talk or type".
- **Defer** offered relative steps only, one column per unit (tomorrow / 3 days, 1 / 2 weeks, 1 / 3 months). Anchors such as "next Monday" were rejected. Renamed *Reschedule* (0.4.0), with *Other date …*; *Move* was not used, as it means moving to another journal. The steps are now *Next day* / *2 days*, the same for every entry; for a series they count from the occurrence, and the sheet adds *Skip* / *Delete series*.

### 4.3a Pickers and menus on phones (after the first beta tests)

- Date and time are chosen with the system's own pickers, laid invisibly over the calendar and clock icons, because opening a hidden field from script did not work reliably on iOS. Time has *from* and *to*.
- A new item can get its date from a calendar button in the add field; without it, the item is for today.
- The tag menu opened downwards and ran out of the visible area on phones; it is now a sheet at the bottom of the screen on phones, and opens upwards on wide screens when there is no room below.

### 4.3b Manual edit of the text (after the first beta tests)

Editing the working copy as free text applied every keystroke at once, did not show that anything was pending, and could not delete entries. It now has an explicit mode: *Manual edit* makes the field editable and adds a box per line in a gutter (as in a mail program; ticked lines are removed with *Delete*). A first version that turned every line into a separate field was rejected: the text must stay a text field that can be edited in place and copied as a whole. Changes are collected and shown as a summary like a commit message, a strict check refuses lines that cannot be read instead of correcting them silently, and only *Save* writes. Deleting a line closes the entry with `#done`, because in the journal deletion is closing.

### 4.3c Undo

A short undo buffer (five steps, Ctrl-Z, an *Undo* bar on phones) was added after a facet had been turned into a topic by mistake. Undoing writes the earlier content as new revisions instead of rewriting history, so that it synchronises like any change.

While building it, a race was found and fixed: a change made while a synchronisation was waiting for the network was overwritten when the working copy was rebuilt at its end. The rebuild is now skipped when the working copy changed in the meantime, and another synchronisation follows.

### 4.4 Filter (ui.md 4.14)

- The facet bar is always visible in the list, styled like the legend of the outheis web interface (coloured line, name, count; hidden values at 20 % opacity).
- The other tags are in a filter tab (funnel). Showing the results inside the tab was considered, but the tab already needs the space; the result appears in the list, with a line naming the filter and *Reset*.
- *Reset* clears the tab's filters and keeps the facet selection.
- No marker in the header for an active filter: a dot was tried and found clumsy; the filter line suffices.

### 4.5 Printing (ui.md 4.13)

One A4 page as a full-width checklist: it is ticked off by hand, photographed and handed back, so that ticked items can be closed. Facets are chosen before printing (preselected from the facet bar); no tags except the facet name; a short reference to each entry's id; room for notes; a footer counting what follows in the next 7 and 30 days. Two earlier layouts were rejected for large type, tiny text and wasted space.

### 4.6 Documentation for users

Conventions such as Tag definitions and journal names cannot be discovered by using the app. They are explained in the user documentation, a site of its own in `site/` (English as the base, German alongside), published by GitHub Pages and opened from *Documentation* at the bottom left; the `?` buttons summarise them and link there. Structure, templates and build follow outheis-docs; the content is never shared with it.

## 5. Several and shared journals (architecture 8.11)

- **Sharing without sending files:** a shared journal is an account of its own; everyone who shares it adds its phrase. The service needs no change. Read-only access was considered (a separate read token) and postponed as unnecessary for now.
- **One view over all journals.** Lists, filters and print span all journals; entries from other journals carry the journal's name; the text view shows one journal at a time (it is one file).
- **Facets decide the journal.** A facet belongs to the journal whose Tag definition declares it. The reservation travels with the journal, so every member's client applies the same rule without settings. New entries, imports and facet changes are routed accordingly.
  *Superseded (0.3.x):* a name does not decide the journal. With several children's journals the same names (`sports`, `school`, `music`) are bound to occur, and a facet of another journal chosen by name moved a calendar entry into a shared journal unnoticed. Now a facet is chosen together with its journal (small label), moving is choosing the first facet of another journal, and a typed name goes to another journal without asking only if that journal is the user's own (architecture 8.11).
- **Facets are kept apart by journal, not forced to be unique.** First decided: facets must be unique across journals, and a facet declared by two journals blocks new entries until renamed. Revised after the first beta tests: different people cannot be kept from using the same names (`family`, `sports`). A facet is now identified by journal and name; where a name occurs in several journals, the views add the journal's name (`familie · Familie`) and the facet choice asks which one is meant. Considered: appending the journal's name to the tag itself as a third element; rejected because it would have to be stripped again when writing back, so that the owner's journal keeps the name the owner chose. The qualification therefore exists only in the views.
- **Entries in the "wrong" journal** were offered a move or *Keep* in a notice. *Superseded (0.3.x)* together with automatic routing: there is no wrong journal any more, only the one the user chose; moving is choosing the first facet with another journal's label. Moving keeps the entry's `#id` (with a new `#rev`), so that `#ref` and overlays survive; it used to create a new id.
- **Topics need not be unique.** They route nothing, and different people may well use the same topics. A new topic's definition can be written to one, several or none of the journals.
- **A new facet asks which journal it belongs to** when there is more than one journal; with one journal nothing is asked.
- **Values without entries are not shown** in the facet bar and the filter tab (for example the old name after a rename, until compaction removes closed entries carrying it).
- **Tag values are lower case.** Every client lowercases tag names and values when it parses a line, whatever was typed or imported; the text of an entry keeps its case.
- **Rename tag** rewrites one value in one journal as new revisions. A free text search-and-replace was rejected: it would also hit words in the text and could damage ids and grammar.
- **Journal names are display text**, not tags: kept as typed, 1–40 characters, no `#` (it would start a tag) and no line break. A capital first letter is the convention but not enforced; the name fields show `Alice` in light grey as an example.
- **Aliases for other journals.** Everyone who adds a journal may give it an alias of their own, shown wherever the journal's name would be. It is kept in the user's own default journal, so it follows them across devices without changing what others see. The name the creator gave stays the journal's shared name. An unnamed journal is shown as "No name yet" with an offer to name it, instead of a bare code.
- **Journal names are entries in the journal** (`Journal name:`), so that all members see the same name; a name kept only in each client would diverge.

- **The journal list belongs to the account** (15 November 2026). Journals were kept per browser; a journal added in one browser was missing in every other one, and on iOS Safari and the home-screen app keep separate storage. Each journal is now recorded with its phrase in an encrypted `Journal key:` line of the default journal, so all clients of the account hold the same journals. The service keeps nothing but the journal files. Accepted consequence: the phrase of the default journal opens all journals of the account.
- **Only the owner deletes a journal on the server.** A journal created with *Create a new journal* is `own`, an added one `joined`; *Delete on server* is offered only for `own`. A separate deletion secret was considered: it would need the service to store something besides the journal file, and it would not protect anyway, because whoever holds the keys can empty the journal with a replace. The rule is therefore kept by the client only. A client holding a joined journal that comes back empty stops sending to it, so that it is not recreated.
- **Passing a phrase by QR code, read in the app.** Considered: a link `…/#join=<words>` opened by the phone camera (puts the phrase into the browser and its history), a link with a second, short code word (a found link can be brute-forced offline, as the words are natural language; only a PAKE would prevent that, too complex for the purpose), and a one-time hand-over through the service (needs data on the service besides the journal file). Chosen: the QR code holds the words, and the receiving app reads it with its own camera view (jsQR, Apache-2.0, embedded); nothing passes through a URL or the service. On a computer the words are typed.
- **Who uses a journal** (architecture 8.4a). Considered: an owner line and member lines in the shared journal; rejected, because every member can write or copy any line. Chosen: a member ID per person and journal, sent with every request, counted by the service. Not the account ID of the default journal (the service could link who shares with whom). The service may refuse requests without member ID, but cannot check that an ID is real without that link. The table is kept in memory; whether it is kept on disk (`-members-dir`) is open (section 7).
- **Diagnostic log** in the browser, optional, without entry text or phrases, to trace faults reported by testers.

- **Note of an entry** (architecture 2.4). Additional text up to 500 characters inside the line, opened by its own button next to `+` (the `+` menu is for tags), as `{{…}}` before the tags, shown in the list only as an icon. It corresponds to `DESCRIPTION` in iCalendar. Delimiters: ASCII, available everywhere, as unlikely as possible in a title; `"…"` occurs in titles, `[[…]]` is a link in wikis and Obsidian, `«…»` is not on every keyboard. Escapes as in JSON (`\n`, `\}`, `\\`).
- **Up to three facets per entry** (architecture 3.3). Asked for by a user whose projects belong to several areas at once. The first facet owns the entry (journal and colour); filters and counts use all of them. Only the first facet decides the journal, because an entry lives in one journal; further facets move nothing. Older clients would move extra facets into the text, so such journals declare version 0.3.0.
- **Two dates with a repetition** (architecture 4.4a). Two `#date` tags stay; a combined form `#date-A:B` was considered and rejected. The distance of the dates decides: closer than one period of `weekly`/`biweekly`/`monthly`/`yearly` is one occurrence over several days that repeats (a yearly window shorter than a year cannot mean anything else), otherwise the dates bound the series and the time applies to each occurrence. Nothing is prevented; the reading is shown, and doubtful cases are marked rather than flagged with `#review-needed`, which a client would set again at every sync while the case persists.
- **Moving facets** (architecture 8.11d). An entry lives in one journal only; a move leaves a tombstone, not a closed copy, which would count as done. Only entries whose first facet is moved go along; the effect on entries that carry it as a further facet (they lose it) may be wanted or not and is to be watched in use. Tombstones are removed after 30 days; a member who shares only the old journal and is offline longer might see the entry again until someone who has both journals syncs.
- **Overlay of a whole journal** (architecture 8.11c). Giving all entries of the children's journals the facet `family` by tagging each of them was rejected: it needs one line per entry and misses entries added later. One line per journal does neither; a finer overlay (only one facet of a journal) is left until a case asks for it.
- **One definition per value and journal** (architecture 3.4). Identical duplicates (as left by merging two values) are closed automatically, because nothing is lost; differing descriptions are left to the user.
- **Tag overlays** (architecture 8.11c). Members want their own classification of shared entries (`family` on each child's entries) without changing what the others see. Considered: a marker on the tag in the shared line (`#facet-family-<member id>`), hidden by other clients; rejected in favour of an overlay line in the own default journal, as for the alias: nothing in the shared journal, nothing others' clients must know. Facets and topics only, because they add; date and time would contradict the entry and need "show the original" everywhere, so preparations are entries of their own with `#ref`. Overlays are volatile by nature; they follow the entry's id and are closed when it is gone.
- **Several of a set is chosen like the facet bar** (ui.md 2.3b); one of a few fixed options as text tabs like the journal tabs; checkboxes only for marking lines. A framed segmented field (an iOS pattern) had been introduced for the rename dialog alone and was removed: it occurred nowhere else in the app.
- **Claim: "open" instead of "free"** (link preview, guide). Whether the service stays free of charge cannot be promised for all time; that the software is open can.
- **Example tags and entries** (ui.md 4.11i). A non-technical user must be able to get rid of the starter content without editing the text, yet keep what they have already tried out with it. Hence a one-time *Delete / Keep* in the settings, and on *Delete* a dialog per own entry carrying a starter value (keep, move to another or a new value, delete or remove the topic). The choice is recorded in the journal (`Journal examples: kept|deleted`), not in the browser, so that it is not asked again on another device. The fallback that offered `private` and `work` in a journal without facets was removed, as it brought the examples back after deleting them.
- **Values offered are the open ones of the current state** (architecture 3.4). A renamed facet kept being offered, because the client also read earlier revisions of entries and closed lines. Finished entries still show their old values; only the choice lists changed.
- **Icons in the text line, words below** (ui.md 4.4). The recurrence mark was a glyph among the verbal state markers and cost a line of its own on phones; it now stands as the first icon after the text, before the note icon. The state markers (`required`, `now`, `high`, `review`) are words and stay below.
- **Search in the client** (ui.md 4.14a). The service cannot read the journal, so search runs in the client over all journals; it ignores the horizons and group limits, otherwise the entry one is looking for would be hidden. Closed entries only on request (*include done*), greyed.
- **Header on phones in two rows**: title and the four icons above, status and the views *List* / *Text* below, right-aligned. The magnifier did not fit next to the funnel otherwise. Wide screens keep one row, the views set off from the icons.
- **Facet bar in two rows, ordered by assignment** (ui.md 4.14). With many shared journals the bar would push the list off the first screen. Folding alone would show an arbitrary selection, so the bar is ordered by how often facets are assigned; switched-off facets always stay visible; the order changes at most once a day, because moving buttons break habits.
- **Date binding instead of appointment versus task** (architecture 5.5, 0.4.0). Everything passed used to stay in Today as overdue, imported appointments of last week included. The distinction that matters is what happens when the date passes: appointments can be movable or bound to their day, tasks can be flexible or due exactly then. Hence `#type-fix` / `#type-flex`, chosen explicitly when adding; heuristics (calendar origin, repetition, clock time) only fill in where no tag exists. A fixed item that passed waits in *Past* for *Done* or *Reschedule*, so that a cancelled visit can be set anew; a flexible one is carried to Today as *now*, derived and not written. Calendar imports and journals of fixed dates (`Journal type: fixed`, set by the owner, valid for all members) pass without asking.
- **Exceptions of a series** (architecture 4.4b): `#skip-<date>` on the series, and a single entry with `#ref` to the series for a rescheduled occurrence — the iCalendar model (`EXDATE`, `RECURRENCE-ID`), so calendars exchange them without loss.
- **Facet bar by name, facets by journal in the filter tab.** With several people's journals the same names occur (`sport` for each child); in the overview one wants `sport` for all, and the bar has no room for one button per journal. The bar therefore has one button per name across journals; the per-journal choice is in the filter tab, where there is room. To be tried out.
- **Selection mode of the facet bar** is entered with *None* and left with *All*. A first version derived it from whether more facets were off than on; choosing one facet more than half turned the bar over (the chosen ones vanished into the folded part), so the mode now follows the user's action, and the chosen facets keep the order in which they were chosen.
- **Facet order by use, as an experiment** (ui.md 4.14b). Use (assigning, filtering, seeing in Today/Tomorrow) predicts the facets needed better than counts, but the heuristic is uncertain: the third signal reinforces itself, and weights and half-life are guesses. Hence opt-in, with every decision logged and a daily measure (share of uses in the folded bar). The state is one line in the journal, so it follows the user to all devices; signals are kept in the browser and folded in once a day, so that the journal does not get a revision per click.
- **Import preview without a question.** "Is this read correctly?" offered no answer and was removed; with nothing to import only *Close* and the reasons remain.
- **The tag menu is placed again after its content changes** (second step of `+`). Reaching beyond the window, it made the browser scroll when its field got the focus, which closes Safari's date picker. Verified in Chrome only.
- **Journal version** (architecture 3.7). Follows the version of the release (`VERSION`, also the service binary), but is written into a journal only when it first uses a feature older clients would misread, so that ordinary updates do not make older clients read-only. A client older than the journal reads it but sends nothing.

## 6. Bots and language models (architecture 8.12)

- **Rule-based tidying needs no bot.** Removing duplicates, normalising order and compacting are done by every client, without asking, marking what it changes.
- **Bots** run as a Node or MCP client, started by cron or by the scheduler of the host. They write only proposals, questions, comments and learned rules, marked `#source-bot`; comments start with `> ` as in outheis-beta. Nothing takes effect without a human's acceptance.
- **Principles** adapted from Isaac Asimov's Three Laws of Robotics ("Runaround", 1942; *I, Robot*, 1950).
- **Learned rules** are entries `Learned Rule: …`, effective only once accepted, like Tag definitions written by humans.
- **Enforcement** is done by clients on every merge; a bot holding the phrase cannot be prevented technically from writing, so the phrase is given only to trusted programs.
- **Reliability** is uncertain and is measured by accepted versus rejected proposals.

### 6.1 Shared core module

The client logic is in `clients/core/agenda-core.js`, used by the web client (inlined by `clients/web/build.py`, so the web client stays one file) and by the Node client. Rewriting the logic in Go was rejected: two implementations drift apart.

### 6.2 Version and documentation site

A version number and a link to the documentation sit at the bottom left, as in outheis-beta. The version lives in one file (`VERSION`); the build writes it into the web client and names the offline cache after it, which replaces the cache counter that had to be raised by hand. The documentation is the GitHub Pages site of the repository, `outheis-labs.github.io/outheis-agenda` (a site at `outheis-agenda.github.io` would need an organisation of that name), built from the Markdown files into `docs/html/`.

## 6.3 Calendar files (15 November 2026)

Import and export of calendar files, single and in batches, were set as a core feature: there is no good way to aggregate several calendars (work under an administrator's rules, private, a provider such as Proton), and the agenda can be the common source because files can always be moved, whatever an administrator blocks. Import and export run entirely in the client. Re-imports are recognised by a hash of the event's `UID` (`#cal`), so that an updated invitation changes the entry instead of adding a second one. Recurrence is taken over only where the grammar expresses it exactly; anything else is imported once and marked for review rather than approximated silently.

Two further steps were noted and deferred: fetching subscribed calendar addresses in the nightly run of the Node client (browsers usually cannot fetch them), and letting other calendar programs subscribe to the agenda, which needs plain text outside the client and therefore touches the trust model of section 2.1.

## 6.4 Several servers (draft, open; 18 November 2026)

Today a journal lives on one server, and the client knows which. With several servers a journal has to be found without a central directory. Considered, in this order:

1. **The client knows where a journal lives.** Codes and key lines carry the address of the home server; the client talks to several servers directly (CORS allows it). Servers need no knowledge of each other. First step.
2. **Mirrors.** Servers keep copies of encrypted files for each other; lines merge by id and revision, conflicts stay with the clients. For availability, later.
3. **Finding a journal on an unknown server.** Either a search with a hop limit (each server knows a few others; with five each and three hops at most 155 servers are asked, once), started as a background search to see whether it is worth it; or a distributed hash table, for which the journal id (a hash already) is the natural key and a lookup takes logarithmically few hops.

Forwarding by servers on behalf of clients in general (a server asks its peers whenever it lacks an id) was rejected: most new attack surface, little that 1 does not give.

**Privacy.** Today only the home server knows which address uses which journal (the token is in a header; the network sees only that an address talks to the server). A table "journal X is on server Y" on other servers would add parties who know that X exists, where, and when it is looked for. Three rules keep this small:
- **Blinded key:** the table holds a hash of the journal id, not the id; whoever sees an entry can do nothing with it at the home server.
- **Lookups only through the own server:** the user's address stays where it is today; other servers see only the server's address.
- **Short-lived entries:** the home server renews them regularly, otherwise they expire after hours; nothing lies with third parties for good, and a journal that is switched off disappears from the table by itself. The rule that a server keeps nothing but the encrypted file holds: these entries live in memory only.

**Deleting and replacing across servers.** A server holding a copy must not be able to roll a journal back, serve a shortened state or declare it deleted. Required before any copies between servers: the owner gets a signing key pair (e.g. Ed25519); deleting and replacing count only with the owner's signature, which every server can check without reading the content (appending likewise with the allies' key). A mirror never replaces a longer state by a shorter one without such a signature. The clients remain the last instance: they know their last state and the highest revision and already detect and offer to restore vanished lines (architecture 6.4a).

## 6.5 PIN for the browser store (18 November 2026)

Everything the web client keeps lies encrypted under a PIN of six to twelve digits, asked for when the app opens (architecture 8.14). On by default; it can be switched off on purpose, because a device in a kitchen that the whole family uses would be impractical with it. A rule that allowed switching it off only when a device holds no owner words other than those of its own journal was rejected: what deserves protection is the content, not the role, and the app cannot judge the content (an own journal may matter more than a shared one that is public anyway). The app says plainly what is unprotected; the documentation recommends guest or ally codes only on shared devices.

Rejected: passkeys and device unlock (WebAuthn) as an alternative to the PIN: they depend on an operating system, a browser and a key store that someone else controls, bind to the person who set up the device, and do not work for a local journal file. Forward secrecy was considered and dropped: a journal's current state has to stay readable for everyone entitled to it, so it would protect only superseded lines, at the price of member lists and device management. Binding the owner's rights to devices (an owner key per device, the words alone giving ally rights, a delayed recovery) was considered against stolen words and deferred: a device does not stand for a person, several people use the same device and even the same browser. The thought is kept for later.
